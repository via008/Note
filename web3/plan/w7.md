## W7 与 W6 的关系

W6 的 Playground 到 `sendTransaction` 为止，但一笔交易真正被“授权”，发生在 **签名** 那一刻。

**Transaction 的签名在发送之前，但 Signature 本身可以脱离 Transaction 独立存在。** 这正是 W7 要拆开的东西。

W7 的核心问题是计划里那句：**“用户到底签名了什么？”**

## 周一（1h）· 签名体系：EOA / Smart Account / Signer / Signature

### 学习（1h）

**目标**：能区分“钱包”“账户”“签名者”“签名”四个概念，能说出一笔交易签名和一条消息签名的区别。

**任务**：

- [ ] 建立概念分层：

```text
Wallet      → 管理密钥 + 提供签名界面（MetaMask / Rabby / 硬件钱包）
    ↓
Account     → 链上身份（EOA / Smart Account）
    ↓
Signer      → 实际执行签名的实体（私钥 / 合约逻辑 / Session Key）
    ↓
Signature   → 签名的产物（65 字节 ECDSA 签名）
```

- [ ] 区分两类签名：
  - **Transaction Signature**：授权一笔状态变更，签完直接广播
  - **Message Signature**：只证明“我同意某段数据”，不广播、不上链（除非后面有人拿它去上链）

- [ ] 读 MetaMask 文档的 Sign data 章节，理解 `personal_sign` 和 `eth_signTypedData_v4` 的定位差异

**验收**：合上文档，能回答“钱包和账户是一回事吗？”和“Message Signature 和 Transaction Signature 的本质区别是什么？”

## 周三（1h）· Sign Message（EIP-191 / personal_sign）

### 开发（1h）

**目标**：能请求用户签名一段文本，并展示签名结果。

**任务**：

- [ ] 加输入框：用户输入一段 message
- [ ] 用 `walletClient.signMessage({ account, message })` 请求签名
- [ ] 展示签名结果（`0x...` 的 65 字节签名）
- [ ] 在 MetaMask 弹窗里 **仔细观察**：它显示了什么？显示的是明文还是哈希？

**关键理解**：

`personal_sign` 在签名前会做一步预处理：

```text
\x19Ethereum Signed Message:\n<length of message> + message
```

然后对拼接后的内容做 keccak256，再签名。

**为什么要加前缀？** 防止用户签名的“消息”被伪装成一笔交易的签名。没有前缀，攻击者可能诱导用户签一段看起来像消息、实际却是交易哈希的字节。

**验收**：能请求签名并拿到 signature，能说出 `personal_sign` 的预处理做了什么。

## 周四（1h）· Sign Typed Data（EIP-712）

### 开发（1h）

**目标**：能构造一个 EIP-712 结构化的签名请求，并在钱包里看到结构化字段。

**任务**：

- [ ] 定义 `domain`：`{ name, version, chainId, verifyingContract }`
- [ ] 定义 `types`：自定义一个简单的结构，如：

```ts
const types = {
  Mail: [
    { name: "from", type: "address" },
    { name: "to", type: "address" },
    { name: "contents", type: "string" },
  ],
} as const;
```

- [ ] 定义 `message` 和 `primaryType: "Mail"`
- [ ] 调用 `walletClient.signTypedData({ account, domain, types, primaryType, message })`
- [ ] **在 MetaMask 弹窗里对比**：它和 `personal_sign` 的显示有什么区别？

**关键理解**：

EIP-712 的核心价值是 **钱包能渲染结构化字段**。`personal_sign` 只能显示一段文本，而 `signTypedData` 能显示：

```text
from: 0xabc...
to:   0xdef...
contents: "Hello"
```

这就是为什么链上协议（Permit、订单、投票）都用 EIP-712。**用户能看懂自己签了什么，而不是盲签一段十六进制。**

**验收**：能构造并签名一个 EIP-712 消息，能在钱包里看到结构化字段。

## 周六（2h）· 签名验证 + 钱包架构理解 + 签名实验

### Part A：签名验证（1h）

**目标**：理解签名可以被任何人验证，且验证不需要私钥。

**任务**：

- [ ] 用 `verifyMessage` 验证 EIP-191 签名：

```ts
const valid = await publicClient.verifyMessage({
  address: connectedAddress,
  message: "你签的原文",
  signature,
});
```

- [ ] 用 `verifyTypedData` 验证 EIP-712 签名
- [ ] 用 `recoverMessageAddress` 从签名反推出签名者地址
- [ ] 关键问题：**验证签名需要什么？** 答：地址 + 原文 + 签名。不需要私钥。

**理解**：签名的本质是“用私钥对数据哈希做运算，产生一个可被公开验证的证明”。验证者只需要知道“这个地址对应的公钥”和“原文”，就能确认签名是否来自该地址。

### Part B：钱包架构对照（0.5h）

**任务**：

- [ ] 画出当前 Wallet Lab 的架构：

```text
React Component
    ↓
walletClient (viem)
    ↓
window.ethereum (MetaMask Provider)
    ↓
MetaMask 内部：私钥管理 + 签名界面
    ↓
签名结果返回
```

- [ ] 标注：**私钥从未离开钱包**。DApp 拿到的只有地址和签名。
- [ ] 标注：**Signer 在钱包内部**，DApp 通过 JSON-RPC 请求签名，不接触私钥。

### Part C：签名实验（0.5h）

**任务**（至少完成 2 个）：

- [ ] **拒绝签名**：在 MetaMask 弹窗点拒绝，记录 `error.code`（应该是 `4001`）
- [ ] **签名后再验证**：用 `recoverMessageAddress` 从签名反推地址，对比是否和连接地址一致
- [ ] **篡改验证**：把原文改一个字，再 `verifyMessage`，看是否返回 `false`
- [ ] **对比两种签名**：对同一段内容分别用 `personal_sign` 和 EIP-712 签，看钱包显示差异

**验收**：至少 2 个实验完成，每个记录：操作 → 观察 → 解释。
