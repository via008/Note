# W6 每日计划 · Transaction Playground

> **节奏**：周中 4 天 × 1h + 周末集中 4h
> **总预算**：8h
> **核心产出**：Transaction Playground + 3 个 Debug Case
> **原则**：周中推进度、看数据，周末做整合、复现异常、复盘

***

## 总体分配

| 时段 | 时长 | 定位         | 内容                            |
| -- | -- | ---------- | ----------------------------- |
| 周一 | 1h | 学习         | 交易生命周期 + Receipt 数据模型         |

## 周一（1h）· 交易生命周期与 Receipt 数据模型

### 学习（1h）

**目标**：能口述一笔交易从构造到 Receipt 的完整路径，能说出 Receipt 每个字段的含义。

**任务**：

- [ ] 读 viem 文档 `sendTransaction` 与 `waitForTransactionReceipt`（约 20min）
- [ ] 在 Sepolia Etherscan 找一笔成功的 ERC20 transfer，逐字段读：
  - Transaction 页：`from` / `to` / `value` / `nonce` / `gas` / `gasPrice` / `input data`
  - Receipt 页：`status` / `gasUsed` / `logs`
- [ ] 再找一笔 `status = reverted` 的交易，对比差异
- [ ] 用自己的话写下：**Hash 什么时候产生？Receipt 什么时候产生？为什么 Pending 交易没有 Receipt？**

**验收**：合上文档，能解释清楚上面三个问题。

***

## 周二（1h）· Playground 骨架 + 构造请求

### 开发（1h）

**目标**：页面能输入 `to` / `value` / `data` / `gasLimit` / `nonce`，并展示构造出的 `TransactionRequest` 对象。

**任务**：

- [ ] 新建页面 `/playground`
- [ ] `useState` 管理 5 个输入字段
- [ ] 用 `viem` 的 `createWalletClient` + `createPublicClient` 初始化客户端（**不用 wagmi hook**）
- [ ] 点击“构造”后展示请求对象：`to` / `value` / `data` / `gas` / `nonce` / `chainId`
- [ ] `value` 用 `parseEther` 转换，同时显示 wei 和 ETH

**关键点**：构造阶段先不发送，只展示对象。

**验收**：输入地址 + 0.001 ETH，页面显示完整请求对象。

***

## 周三（1h）· 发送 + Hash + Pending 展示

### 开发（1h）

**目标**：点击“发送”后钱包弹出，签名后拿到 Hash，并展示 Pending 状态。

**任务**：

- [ ] 加“发送”按钮，调用 `walletClient.sendTransaction`
- [ ] 拿到 Hash 后立刻渲染 + Etherscan 链接
- [ ] 加状态机：`idle → signing → pending → confirmed / failed`
- [ ] 捕获 `error.code === 4001`，展示“用户拒绝”

**关键点**：这一步只到 Hash，不等待 Receipt；刻意让 Pending 可见。

**验收**：能发出一笔 Sepolia 交易，看到 Hash，点链接能跳 Etherscan。

***

## 周四（1h）· Receipt 展示 + 原始 Log

### 开发（1h）

**目标**：交易确认后展示完整 Receipt，包括原始 Logs。

**任务**：

- [ ] 用 `publicClient.waitForTransactionReceipt` 等待 Receipt
- [ ] 展示 `status` / `gasUsed` / `blockNumber` / `logs`
- [ ] `logs` 先原样展示（`topics` / `data` / `address`），不解码
- [ ] 状态机从 `pending` 进入 `confirmed` 或 `failed`

**关键点**：revert 的交易也有 Receipt，`status = "reverted"`，不是“没收到”。

**验收**：一笔成功 transfer，页面展示 Receipt 和至少一条 Log。

***

## 周六（2h）· Log 解码 + calldata 反解 + 异常复现

### Part A：Log 解码 + calldata 反解（1h）

**目标**：把原始 Log 解码成可读事件，把 calldata 反解成函数调用。

**任务**：

- [ ] 用 `parseEventLogs` + ERC20 ABI，把 `Transfer` 解成 `from` / `to` / `value`
- [ ] 页面展示：事件名 + 参数
- [ ] 加“calldata 反解”小工具：粘贴 `data` + ABI，用 `decodeFunctionData` 解出函数名和参数
- [ ] 用真实 ERC20 transfer 验证：`data` 能解出 `transfer(address,uint256)`

**关键点**：ABI 就是告诉你怎么把字节翻译成函数和参数；`topics[0]` 是事件签名哈希。

**验收**：给一笔 transfer，页面显示 `Transfer(from, to, value)`。

### Part B：异常复现（1h）

**目标**：至少复现 2 个异常，记录现象 → 错误 → 根因。

**任务**（至少完成 2 个）：

- [ ] **User Reject**：钱包点拒绝，记录 `error.code`
- [ ] **Revert**：调用必然 revert 的合约，看 Receipt.status
- [ ] **Insufficient Balance**：value 设 100 ETH，看哪一步失败
- [ ] **Invalid Address**：`to` 填 “abc”，看前端还是 viem 抛错
- [ ] **Wrong Network**：钱包切主网，看 chainId 不匹配错误

**每个 Case 记录**：

```markdown
### Case：User Reject
- 现象：
- 原始错误：
- 发生阶段：（构造 / estimate / 签名 / 发送 / 等待 Receipt）
- 根因：
- 解决 / 解释：
```

**验收**：2 个 Case 记录完整，能说出错误发生在生命周期哪一步。
